# CoolingCtrlBoard RT-Thread BSP Design

## Goal

Build a standalone RT-Thread Studio project for the custom CoolingCtrlBoard V1.0 hardware. The project shall use RT-Thread Standard v5.2.2, target the STM32F302CCT6, compile with GNU Arm GCC, and register the board's USART1, ADC1, CAN, and GPIO resources through the RT-Thread device framework.

The first milestone is a clean GCC build and a project that can be imported into RT-Thread Studio. Temperature-control application logic, heater regulation algorithms, and hardware flashing are outside this milestone.

## Source Baseline

- RT-Thread source: official `RT-Thread/rt-thread` release tag `v5.2.2`.
- Structural BSP reference: official `bsp/stm32/stm32f302-st-nucleo`.
- Hardware configuration reference: `CoolingCtrlBoard_CubeMX/CoolingCtrlBoard_CubeMX.ioc` and its generated source.
- RT-Thread distribution: Standard, not Nano.
- No code is taken from unofficial forks.

The Nucleo BSP is used only for its proven STM32F302 Cortex-M4F port, SCons/Kconfig structure, and shared STM32 driver integration. All Nucleo-specific clock, memory, pins, console, LED, and button settings are removed or replaced.

## Directory Layout

The implementation produces two task-owned directories without overwriting the CubeMX project:

```text
RT-Thread-v5.2.2/
  bsp/stm32/cooling-ctrl-board/   Custom BSP source used to build and regenerate

CoolingCtrlBoard_RTThread/        Standalone RT-Thread Studio import project
```

`CoolingCtrlBoard_CubeMX/` remains the source of truth for chip pin selection and clock/peripheral timing. It is not used as the RT-Thread build root.

## MCU and Build Configuration

- MCU: STM32F302CCT6, package LQFP48.
- Device macro: `STM32F302xC`.
- CPU: ARM Cortex-M4F.
- FPU: FPv4-SP-D16.
- Floating-point ABI: hard.
- Flash: 256 KiB at `0x08000000`.
- SRAM: 40 KiB at `0x20000000`.
- Startup file: `startup_stm32f302xc.s` generated by CubeMX or an identical official GCC startup file.
- Linker script: 256 KiB Flash and 40 KiB SRAM, based on `CoolingCtrlBoard_CubeMX/STM32F302XX_FLASH.ld` and extended with the RT-Thread initialization sections required by the selected BSP framework.
- Compiler: the GNU Arm GCC toolchain used by RT-Thread Studio, provided that it successfully compiles RT-Thread v5.2.2. If Studio's bundled GCC 5.4.1 rejects current RT-Thread code, the project remains GCC-based and is configured to use a compatible newer GNU Arm toolchain rather than downgrading RT-Thread.

## Boot and Clock Architecture

RT-Thread owns the startup path, vector table, scheduler exception handlers, and system tick.

The CubeMX-generated `main.c`, `stm32f3xx_it.c`, `syscalls.c`, and `sysmem.c` are not copied into the BSP. In particular, the CubeMX implementations of `SysTick_Handler`, `PendSV_Handler`, and `SVC_Handler` must never replace the RT-Thread Cortex-M4 port.

The board clock implementation uses:

```text
External crystal HSE: 8 MHz
PLL input divider:    1
PLL multiplier:       9
SYSCLK/HCLK:           72 MHz
APB1:                  36 MHz
APB2:                  72 MHz
USART1 clock:          APB2, 72 MHz
ADC12 clock:           PLL, 72 MHz
```

Clock failure enters the BSP error handler with interrupts disabled. There is no automatic fallback to HSI because running peripherals at an unexpected clock would invalidate UART and CAN timing.

## HAL and Driver Ownership

Only one STM32F3 HAL implementation is compiled: the HAL bundled by the RT-Thread v5.2.2 STM32 BSP libraries. The generated `CoolingCtrlBoard_CubeMX/Drivers` directory is not copied into the RT-Thread build, preventing duplicate types, symbols, and HAL versions.

CubeMX-generated initialization code is used as a hardware reference:

- System clock fields are adapted into the BSP clock function.
- GPIO modes, alternate functions, pull settings, speeds, peripheral clocks, and NVIC settings are adapted into RT-Thread board and MSP initialization.
- `MX_ADC1_Init`, `MX_USART1_UART_Init`, and `MX_CAN_Init` are not compiled alongside RT-Thread device drivers when they define duplicate HAL handles.
- RT-Thread owns the UART, ADC, and CAN HAL handles and interrupt dispatch through its STM32 common drivers.

The BSP enables the required HAL modules in `stm32f3xx_hal_conf.h`: GPIO, RCC, Cortex, PWR, Flash, UART, ADC, and CAN.

## Console and USART1

USART1 is the initial RT-Thread console and FinSH/MSH device:

```text
TX:              PB6, GPIO_AF7_USART1
RX:              PB7, GPIO_AF7_USART1
Baud rate:       115200 bit/s
Frame:           8 data bits, no parity, 1 stop bit
Flow control:    none
Oversampling:    16
TX pull:         none
RX pull:         internal pull-up
GPIO speed:      high
Receive method:  interrupt-driven, no DMA
```

The BSP enables USART1 and its IRQ through the RT-Thread STM32 serial driver. A duplicate CubeMX `USART1_IRQHandler` is not compiled.

## GPIO Safety and Board Pins

The board exposes two application-level GPIO resources:

- PB0, schematic net `HTR_PWR`: push-pull output, no pull, low speed.
- PB15, schematic net `LS`: digital input, no internal pull.

PB0 is driven low before it is configured as an output and before the scheduler starts. This prevents heater activation during startup or reset. Application code must explicitly request heater activation; the BSP never defaults it high.

PB15 relies on the board's external 10 kOhm pull-up and RC filter. A closed switch reads low. The first BSP uses polling; EXTI15 is not enabled.

Pin aliases are documented in `board.h` using RT-Thread pin numbers obtained from the STM32 pin driver instead of hard-coded application-private arithmetic.

## ADC1 Device

ADC1 is registered through the RT-Thread ADC device framework. The three physical inputs are:

```text
PA0 / ADC1_IN1 / NTC_ADC0
PA1 / ADC1_IN2 / NTC_ADC1
PA2 / ADC1_IN3 / HYSN_ADC2
```

All three GPIO pins use analog mode with no pull. ADC operation is single-ended, 12-bit, right-aligned, software-triggered, single conversion, and non-continuous. DMA and ADC interrupts are disabled for this milestone.

Each `rt_adc_read()` operation selects one channel as regular Rank 1. The STM32 ADC driver configuration uses `ADC_SAMPLETIME_181CYCLES_5` for channels 1, 2, and 3. The application may read all three channels sequentially from a 100 ms sampling thread and may average 8 to 16 raw readings per reported value.

ADC calibration is performed once after ADC initialization and before the first conversion using the STM32F3 single-ended calibration operation. Calibration failure prevents the ADC device from being reported as ready.

Voltage conversion uses the board's measured `VREF_3V` analog reference, not a hard-coded 3.3 V assumption.

## CAN Device

The on-chip CAN peripheral is registered through the RT-Thread CAN device framework:

```text
RX:               PA11, GPIO_AF9_CAN
TX:               PA12, GPIO_AF9_CAN
Mode:             normal
APB1 clock:       36 MHz
Prescaler:        4
BS1:              15 time quanta
BS2:              2 time quanta
SJW:              1 time quantum
Bit rate:         500 kbit/s
Sample point:     88.9 percent
Automatic retry:  enabled
Automatic bus-off recovery: enabled
```

CAN pin mode is alternate-function push-pull, no pull, high speed. Required CAN receive/transmit/SCE interrupts are provided by the RT-Thread STM32 CAN driver without duplicate CubeMX handlers.

The board contains a fixed 120 ohm termination resistor. The BSP documents this hardware fact but cannot determine whether the assembled board is placed at a physical end of the CAN bus.

The first software smoke test configures a permissive receive filter and exposes the RT-Thread CAN device. It does not define an application CAN protocol.

## RT-Thread Configuration

The initial configuration enables only the components needed for bring-up:

- RT-Thread Standard kernel.
- FinSH/MSH shell and device command support.
- Heap and dynamic object creation within the 40 KiB SRAM budget.
- Pin device framework.
- Serial device framework with interrupt RX.
- ADC device framework.
- CAN device framework.
- Console device set to `uart1`.
- Tick frequency left at the RT-Thread v5.2.2 BSP default unless the F302 reference BSP requires an explicit value.

Filesystems, networking, POSIX compatibility layers, software packages, and temperature-control application services are disabled for the first milestone to preserve RAM and reduce bring-up variables.

## Application Smoke Test

The initial `applications/main.c` performs no heater control. It shall:

1. Confirm that the heater GPIO is low.
2. Print a concise boot message containing the board name, RT-Thread version, and system clock.
3. Locate `adc1`, `uart1`, and the registered CAN device and report whether each is present.
4. Return control to RT-Thread without a busy loop.

Optional MSH commands may expose safe read-only checks for PB15 and ADC channels. No command may turn PB0 on in the first milestone.

## Studio Project Generation

The custom BSP is compiled from the RT-Thread source tree first. After a successful GCC build, a standalone Studio project is produced with the RT-Thread supported IDE distribution command and written to `CoolingCtrlBoard_RTThread`.

The generated project must contain RT-Thread Studio metadata, relative source/include references that resolve on the target machine, the selected GCC flags, the STM32F302xC startup object, and the 256 KiB/40 KiB linker configuration.

The project shall be importable with RT-Thread Studio's "RT-Thread Studio Projects into Workspace" importer without copying the original CubeMX project into the Studio workspace.

## Verification

Verification for this milestone consists of:

1. Confirm the official source tag resolves to `v5.2.2`.
2. Build the custom BSP with GNU Arm GCC without errors.
3. Confirm the linker map uses no more than 256 KiB Flash or 40 KiB SRAM.
4. Confirm the ELF defines the STM32F302xC vector table and RT-Thread scheduler exception handlers exactly once.
5. Confirm no CubeMX `main`, `SysTick_Handler`, `PendSV_Handler`, or `SVC_Handler` duplicates are linked.
6. Confirm PB0 is written low before output-mode initialization by source inspection.
7. Confirm ADC channels 1, 2, and 3 use 181.5-cycle sampling by source inspection.
8. Confirm CAN timing calculates to exactly 500 kbit/s from a 36 MHz APB1 clock.
9. Generate the Studio import project and confirm its expected metadata and build configuration files exist.

Hardware download, UART terminal output, ADC voltage validation, and CAN bus communication require the physical board and ST-LINK and are separate acceptance steps after the build artifact is approved.

## Failure Handling

- Download failure: retry the shallow fetch of only official tag `v5.2.2`; do not silently substitute `master` or an older kernel.
- Compiler incompatibility: use a compatible GNU Arm compiler and update the Studio build configuration; do not downgrade RT-Thread without user approval.
- Duplicate HAL or interrupt symbols: remove generated CubeMX implementations from the build and retain RT-Thread ownership.
- Clock configuration failure: stop in the board error handler.
- ADC calibration failure: report initialization failure and do not return uncalibrated samples.
- Missing peripheral device registration: fail the smoke-test status print while keeping PB0 low.
- CAN bus-off: rely on enabled automatic bus-off recovery and expose error counters through the RT-Thread CAN device rather than resetting the MCU.

## Out of Scope

- Heater control algorithms and automatic PB0 activation.
- NTC resistance-to-temperature curves and pressure calibration.
- CAN application protocol, message IDs, and payload definitions.
- Firmware update or bootloader support.
- Production fault logging, watchdog policy, and low-power modes.
- Publishing the BSP to the RT-Thread SDK manager.
